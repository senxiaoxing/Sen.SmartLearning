# 09 · 竞品借鉴与可采纳项

> **这份文档管什么**：市面主流小学学习 App 各自最强的那一条设计是什么、
> 哪些搬到这个项目里来、搬的时候撞哪条红线、落点在哪。
>
> **不管什么**：具体实现方案（真要做时另开条目）；内容扩展路线（[08](08-年级分区与内容扩展.md)）。
>
> 调研 2026-09-04，取舍已定（同日）。信息来自各家官方页面、应用商店、产品拆解与家长实测反馈。

---

## 0. ⭐ 一句话：它们在解决的问题和我们不是同一个

这七款 App 全都是给**不特定的孩子**做的。做给所有人，就必然面对一件事：
**她随时会走，而你不认识她。** 于是它们把最大的工程量花在对抗流失上——
连续天数、段位排名、抽卡开箱、每日提醒、限时挑战。

这个项目是给**一个**孩子做的。上面那一整类机制到这里全是负资产：

```
她不会流失到别的 App —— 只会不想打开
所以留存靠的不是「断了可惜」，是「这里认识我」
```

反过来，那些 App 因为要服务所有人而**做不到**的事，恰恰是这里的主场：
知道她卡在凑十法的哪一步、记得她上周错的那道题、用她的昵称叫她。

**判据由此而来**：一条设计值不值得抄，不看它在人家那里多有效，
看它靠的是「更懂这个孩子」还是「让她舍不得走」。前者搬，后者一概不搬。

## 2. 已定要做的

### 2.1 ✅ 短文模块（2026-09-05 完成）—— 学自洪恩识字，但**不带语音**

洪恩最强的设计不是识字卡，是那 130 本**分级绘本**：每本只用孩子**已经学过的字**。
识字从「认字」变成「**我能读了**」。

我们的识字 300 现在是一面墙——**字学完就到头，没有下一步**。

#### ⭐ 关键取舍：短文不带朗读，古诗带

这是这个模块最重要的一条，也是它和古诗 60 的全部分工：

| | 面向 | 语音 | 为什么 |
|---|---|---|---|
| **古诗 60** | 低阶（还读不了） | ✅ 带 | 范读是教学内容本身，背诵要靠听 |
| **短文 / 文言文** | 高阶（至少拼音没问题） | ❌ **不带** | 它的目的就是**让她自己读出来** |

英语同构：**单词、短句带语音；英语短文、阅读理解不带。**

两个理由，第二个更硬：

1. **带朗读会削弱它自己的目的。** 那会变成拼音依赖的加强版——
   她听得懂、跟得上，但从来没有独立读过一句。短文的价值就在「她自己读」这个动作上。
2. ⭐ **读音规范的风险不可控。** 古诗那次 TTS 把「鬓毛衰」念成 cuī（古押韵音，
   教材注 shuāi），是它主动往古音上靠。文言文只会更严重，
   而错的读音会跟着她很久。**不做成强依赖，就没有这一整类风险。**

#### ⭐ 于是「语音包到二年级为止」这条红线**一个字都不用改**

短文本身不产生任何语音需求，`voiceManifest` 二年级封版原样成立。
CLAUDE.md 那条红线、design/07、design/08 §1.3 全部不动。

判据甚至更清楚了：**语音是脚手架，能读了就撤。**
这和「十格阵只在难度 1 提供」是同一条原则的另一次应用。

#### ⚠️ 没有朗读之后，「关键字词高亮」的含义变了

有朗读时高亮是**跟读指示**（读到哪亮到哪）；没有朗读，它只能是**静态标注**。
所以要明确它标什么——标「这个字你学过」：

```
✅ 短文用字尽量落在识字 300 表内（分级短文本来就该这样）
✅ 表内的字标出来，点一下能听单字读音 —— 那些字音片段识字墙已经有了，零新增语音
⛔ 表外的字不标色、不给点 —— 点了没反应比没得点更糟
```

这样「高亮」「可点读」「已学过」是同一件事。她卡住时的退路是**一个字**，
不是一整句——不会退化成听朗读。

#### 其余约束

```
✅ 拼音开关（默认开）—— ⭐ 一直挂着拼音她会只读拼音不看字，这是这类模块
   最常见的失败方式。关掉试试自己读，这个开关本身就是「我长大了」的表达
✅ 与识字墙、诗单同一条分辑规矩：追加新辑，不重排、不接长
⛔ 不判对错、不落 attempts、不记 mastery、不给积分、不进宠物经验
   —— CLAUDE.md「语文三块是教不是练」原样适用
```

⭐ **全部价值压在一条测试上**：`hanziStories.test.ts` 逐字扫描，
故事里出现任何一个「本辑之后才学」的字就红。
守不住这条，它就退化成又一堆她读不懂的课文——而「读得懂」正是它唯一的意义。

#### ⚠️ 现代课文有版权，仓库是公开的

古诗、文言文、古代寓言是公有领域，没问题；
但人教版的现代课文原文放进 `dist/` 就是公开可访问的，
「纯自用」在那一刻不成立（design/08 §1.2 已经为题库担心过同一件事）。

```
✅ 文言文、古诗、寓言优先
✅ 现代课文 → 自己写的同主题短文
❌ 不放教材现代课文原文
```

#### ⚠️ 古诗和短文共用同一个朗读器，别做成两套

`PoemView` 那一层（逐字拼音 + 点读 + 高亮）应该抽成共用组件，
古诗、短文、文言文都是它的内容类型——只是古诗那个类型带整句语音，短文不带。

否则加到第三种内容时会有三份几乎一样的播放逻辑，
而 `story:check` 那次的教训正是「另写一套播放逻辑，听到的就不是 App」。

#### ⚠️ 实做后的更正：共用没做，因为**交互单位不同**

上面这条在动手时打了折。`PoemView` 和短文的排版看着像，但：

| | 交互单位 | DOM |
|---|---|---|
| 古诗 | **整句**（背诵要磨的是一句） | 拼音、汉字各一整串 `<span>`，靠字距近似对齐 |
| 短文 | **一个字**（卡住时的退路） | 每个字自成一个节点，否则点不到 |

硬合成一个组件会做出个四不像，而 `PoemView` 是已经上机验过、还接着长按慢速的页面，
为一句设计文档去重构它，风险大于收益。

落点改成新建 `components/RubyText.tsx`（逐字拼音、逐字可点），古诗**没有迁过去**。
真正共用的那层在**数据形状**上——`StoryLine` 与 `PoemLine` 同构（`text` ＋
空格分隔的逐字 `pinyin`，字数由测试校验）。等文言文来了，如果它也是逐字交互，
这个组件已经在这儿了。

#### ⭐ 落点

| 文件 | 做什么 |
|---|---|
| `domain/story.ts` | 类型 ＋ `storyLineChars()` 逐字拆分（纯函数） |
| `data/seed/hanziStories.ts` | 第一辑 8 篇 ＋ `STORY_GLUE` 粘合虚词表 |
| `data/seed/hanziStories.test.ts` | ⭐ 越界扫描等 15 条 |
| `components/RubyText.tsx` | 拼音在上、汉字在下，逐字可点 |
| `features/chinese/StoryLibrary.tsx` · `StoryView.tsx` | 短文单、一篇短文 |
| `playgroundSections.ts` · `App.tsx` | 语文分区末尾追加「短文」，路由 `/stories` |

#### ⭐⭐ 「只用学过的字」实际是怎么做到的

第一辑只有 100 个字，而**「是」「有」「不」「很」「只」全都排在第三辑**——
照字面「只用本辑的字」，第一句话都写不出来。

解法是发现了另一批字：**「的」「了」「在」「和」「也」「就」「都」「个」「们」
一个都不在识字 300 表里**（轻声字被 `hanziCards.ts` 明确排除，其余整表就没收）。
它们成了 `STORY_GLUE`——唯一允许的表外字，屏幕上**不标色、不可点**。

于是三件事对上了：**标色 = 可点 = 有音 = 「这个字你学过」**。

```
✅ 本辑及之前的字        标色、可点、点了念「天。蓝天的天。」（识字墙现成片段）
✅ STORY_GLUE 的虚词     不标色、不可点
❌ 后面辑才学的字        测试直接红
```

⚠️ 有一条测试专门查 `STORY_GLUE` 里**每个字都真的不在识字表内**：
把一个表内字写进去，后果是那个字在短文里失去颜色和读音——等于把她学过的字藏起来，
而这在屏幕上看不出来。

#### ⚠️ 第一辑为什么全是「自己写的」，一篇寓言都没有

§2.1 定的「文言文、古诗、寓言优先」是**版权**排序，不是文体排序。
100 个字写不了文言，也写不了寓言——能用这些字讲完的只能是自己编的日常。
寓言、古文从第二辑起才谈得上。

#### ⭐ 拼音开关刻意**不持久化**

每篇重新打开都回到「开」。记住选择会把「关掉拼音」变成一次性的设置，
而它的价值恰恰在于**每次都由她主动按下去**——那一下就是「我长大了」的表达。
（与诗单不记住选了哪一辑同理。）

按钮放在**正文下面**：她的主线是从上往下读完，开关是读完才用得上的东西，
摆顶部会变成进页面第一眼看到的按钮，反倒像必须先做的选择。

#### ⛔ 渲染出来才发现：折行时句号会独占一行

窄容器（实测 340px）下，**句号被甩到下一行、孤零零占一整行**。
中文排版里句号不能落行首，但浏览器那条禁则**对行内块无效**——
它只管文本字符，每个字自成一个盒子之后，断行机会就落在盒子之间了。

试过改用 `inline-flex` 排进文本流，**没用**（行内块之间照样可断）。
最后是在渲染前把标点并进前一个字那一组，组内 `whitespace-nowrap`。
为此 `StoryChar` 加了 `punctuation` 字段——让 UI 用「没有拼音」去猜是隐式约定，
而这条规则值得写出来。

> ⭐ 又一次「测试全绿、渲染出来才发现」：15 条测试全过，
> 而这个问题只在把容器缩窄之后才看得见。

#### 已验证（浏览器实测）

```
短文单 8 篇              ✅
《大雪》逐字拼音对齐      ✅ 表内字橙色可点、虚词灰色不可点
藏起拼音                 ✅ 字不跳位（拼音行 invisible 保位）
点字发声                 ✅ hanzi0.bin / hanzi1.bin 均 200，无 console 报错
最长句 13 格 × 44px      ✅ 572px < 容器 680px，不折行
窄到 340px               ✅ 折行逐字对齐保持，句号跟着前一个字走
乐园入口                 ✅ 语文分区第五个，与识字不相邻
```

#### ⭐⭐ 上机验收（2026-09-05）：两条反馈，第一条推翻了核心设计

| 反馈 | 根因 | 修法 |
|---|---|---|
| ⭐「为什么『了』『的』『也』没有高亮」，**这些反而最吸引她** | 用颜色编码了一个她不需要知道的信息 | 全部字一个样，见下 |
| 第三辑点进一篇，返回却回到第一辑 | 分辑存在组件 `useState` 里 | 新建 `browseVolumeStore`，见 §2.1a |

##### ⛔ 「标色＝可点＝有音是同一件事」这条设计，错了

原先只给识字 300 表里的字上色，表外虚词灰着、不可点，
理由是「标色的含义是**这个字你学过**」。

**她的反应正好相反**：那个差异成了整屏最抢眼的东西，她盯着问为什么。

想岔的地方是**把系统的分类当成了她的分类**。「的」「了」在她眼里
和别的字一样是句子的一部分——她读的是句子，凭什么有些字被冷落。
而「这个字属不属于某张表」是我们的内部实现，对她毫无意义。

```
✅ 现在：所有字同一个主色、同一个字重、同样可点
⛔ 不要再按任何「这个字属于哪张表」的理由把它们分开
```

`StoryChar.known` 整个删掉了，`storyLineChars()` 也不再需要注入字表——
**渲染数据里根本不该有这一项**，那才是它不会被误用的保证。

##### ⚠️ 于是「点了没反应」要另想办法：**虚词点了给一声轻响**

统一之后她会去点虚词，而那些字没有语音片段。

⛔ **不能用 TTS 补**：`STORY_GLUE` 那 13 个字**全是轻声**，
TTS 会念成本调（的 dì、了 liǎo），那是教错音——正是这个模块
「不做成语音强依赖，就没有整类读音风险」要躲开的东西。

所以有片段的念字，没片段的 `playSfx('tap')`：她知道「按到了」，
但不会把那一声误当成读音。判断落在 `StoryView`，不进渲染数据。

⚠️ **iPad 真机仍未验**：44pt 触控够不够、以及「她是不是真的会自己读」，
只有上机才知道——后者才是这个模块成不成立的判据。

### 2.1a ⭐ 返回时停在她离开的那一批（2026-09-05）

上机反馈：**短文乐园点第三辑 → 进一篇 → 返回，回到了第一辑。**

根因是各页把选中的辑放在自己的 `useState` 里，而返回是导航到另一个路由，
组件卸载、状态随之消失。

#### ⛔ 原先的注释写错了一件事

`StoryLibrary` / `PoemLibrary` 里都写着「选中哪一辑不落库——每次从第一辑打开
也没什么损失」。那是**把两件事混成了一件**：

| | 要什么 | 值不值 |
|---|---|---|
| 跨会话记住上次看到哪 | 一张新的用户数据表 | ❌ 不值 |
| **同一次浏览里返回还在原地** | 一份内存状态 | ✅ 这不是偏好，是**导航的基本正确性** |

她刚从那儿点进去的，退回来当然该在那儿。回到第一辑对她而言
等于「我刚才翻的东西不见了」。

#### 落点：`stores/browseVolumeStore.ts`

一个内存 store，键用**路由路径**（天然唯一，不必再维护常量表）。
刷新整页后回到默认辑是**对的**——那是新的一次浏览，store 的生命周期正好如此。

一并修的五处（同一个毛病）：

```
/playground   ⭐ 最要紧 —— 它是所有浏览内容的中转站，每进一块都卸载一次
/stories      她报的那一处
/poems        点进一首诗再返回
/hanzi        去写字墙或乐园再回来
/pets         翻往届伙伴，进小屋再回来
```

⚠️ `/pets` 需要「点回当前年级＝回到跟随档案年级」这个语义（否则家长改了
档案年级这一页不会跟上），store 因此约定**空串表示回到默认**。

⚠️ 首页的年级切换**不在其中**：它的真相源本来就是 `sessionStore.contentGradeLevel`，
从来不丢。

#### ⚠️ 触控目标在这里放宽到 44pt（CLAUDE.md 要求 88×88pt）

88pt 是给**主线交互**定的（答题选项、首页入口，点不中就做不下去）。
短文里点字是**卡住时的退路**，主线是「用眼睛读过去」。
真按 88pt 排，一行只放得下 3~4 个字，一句话要折成三行——
那会毁掉「连成句子读」这件事本身。44pt 是 Apple 的通用下限，
且字块之间不留空隙，实际可点区域连续。

### 2.2 ✅ 听算（2026-09-05 完成）—— 学自小猿口算

**只报题、不显示算式**，孩子听完在心里算，再从四个选项里挑。

#### ⭐ 更正：不是「敲答案」

方案原本写的是「听完直接敲答案」。**`InputNumber` 其实是四选一，不是键盘输入**，
而它文件头写着两条不能动的理由：

1. 一年级孩子敲键盘慢且易错，**输入本身的摩擦会盖过题目难度**
2. ⭐ **只有四选一才能承载诊断性干扰项** —— 那是整个自适应系统的数据来源

所以听算保持四选一。改成敲答案会丢掉 `misconceptionTag`，
撞 CLAUDE.md 最核心的那条红线。

```
零新音频   数字和运算符的片段早就有了
新增       一个题型 listen_number ＋ 一个薄组件（不显示 stem.text 的 ChoiceAudio）
```

它练的是**完全不同的能力**——工作记忆 + 心算，看着算和听着算不是一回事。
顺带，孩子那句「答题界面单一」在这里得到的是最彻底的回答：**没有界面**。

```
✅ 必须能重听（点喇叭再念一遍），且重听不影响判定 —— 听算考的是算，不是听力
⚠️ 只能一、二年级 —— 三年级起不朗读中文，正好与语音包封版同期结束
⛔ 不做「听一遍就没了」—— 那是考试的框架，不是练习的
```

#### ⭐⭐ 计时必须扣掉听题那一段，不然会歪掉 SM-2

`toRecallQuality` 拿本次耗时与该知识点的**历史均值**比。而听算她得先听完
才谈得上算，同一个知识点里听算恒定慢两秒，于是：

```
看算的题 → 一律「又快又对」（quality 5，间隔拉长）
听算的题 → 一律「还在硬算」（quality 3，间隔压短）
```

### 2.3 ✅ 笔顺演示 + 田字格（2026-09-04 完成）—— 学自 Duolingo ABC，只做前半段

Duolingo ABC 的描红是三段式：看笔顺动画 → 护栏模式描 → 自由模式写。

而洪恩识字的家长吐槽正好指出半吊子做法的问题：
**它加了「写」这个环节却没讲笔顺，对写字没有实际帮助。**

所以只做真正有教学价值的那一半：

```
✅ 笔顺演示（一笔一笔画出来，可重播），田字格里
⛔ 不做描红判定 —— 判笔顺对错要算法，而且判错会踩「答错反馈要温和」
```

#### 技术：取数据，不引库

`hanzi-writer-data` 的数据每个字有 `strokes`（笔画轮廓 SVG path）和
`medians`（笔画中线坐标），坐标系 1024×1024、**y 轴向上**（要翻转）。
CDN 可按字单取，只打包我们用到的 300 字。

动画原理（库自己也是这么做的，所以**引不引库在丝滑度上没有区别**）：
拿笔画轮廓当 `<clipPath>`，在里面画一条沿中线的粗线，
用 `stroke-dasharray` + `stroke-dashoffset` 让它从头长出来。

两个「丝滑」的变量都不在库里：

- ⭐ **每笔时长按中线长度成比例**，不是每笔等时。否则一个点和一个长横一样久，
  看着很假——`hanzi-writer` 默认就是等时的，自己写反而能调对
- ⚠️ **`stroke-dashoffset` 不在 CLAUDE.md 的 transform/opacity 白名单里**。
  它不触发 layout，但触发 paint。单字演示（300 常用字最多二十来笔）在 iPad 上稳，
  但**这条破例要写在组件文件头注释里**，否则下次有人照着性能规范来改就把动画改没了

组件叫 `components/TianGrid.tsx`，和 `TenFrame.tsx` 同一个地位——
田字格是识字写字的通用教具，演示动画和笔顺跟随图共用同一套视觉语言。

§6.4 的兜底「验不了的字就不给笔顺」，实现方式不是加 `strokeOrderVerified: false`，

不存在「标了 true 却没数据」这类自相矛盾的状态。

#### ⭐ 笔画名称：第二个数据源，⚠️ 尚未人工核对

与笔顺图形（makemeahanzi）**各来一处**。两者的笔数必须逐字相等，
否则名称整体错位——那比没有名称更糟。生成脚本对此有硬校验，
对不上直接中止：**100 字实测全部一致**。

清理了两种写法：`点2` → `点`（cnchar 用尾缀数字区分变体）、
`横撇|横钩` → `横撇`（一笔两种叫法，竖杠她读不出来）。

#### ⭐ 每笔时长按中线长度成比例

等时会让「点」和「长横」花一样久——点那一下拖得像在画线，长横又一闪而过。

有一条测试专门锁「短笔画一定比长笔画快」。

⚠️ 基准值来回调过一次，**别再改**：420 →（第一次上机嫌快）680 →
（2026-09-05 再次上机后）**调回 420**。慢下来之后一个字要写十秒，
而她是**反复看这个循环**的，不是只看一遍——耐心耗在等笔画上，
比「看不清那一笔」更劝退。

⚠️ 改它要同步改 `generate-stroke-check.mjs` 里的同名节奏——
校验页是拿来判断笔顺对不对的，快慢不同就不是在看孩子将来会看到的东西。

#### ⛔⛔ 描画绝不能用 framer-motion 的 `pathLength`

第一版用了它，**4 笔的「天」正常，11 笔的「黄」一点开就整页冻结**——
连 JS 都执行不了，不是慢，是死。换回原生 `strokeDasharray` + CSS transition 后正常，
而那正是 `stroke:check` 那一页跑 100 个字都没事的画法。

⭐ 教训：**校验页已经验证过的画法，App 里要用同一套。**

这与 story:check 那次「自己另写一套播放逻辑，听到的就不是 App」是同一个形状。

#### ⚠️ 这一屏是全 App 最重的：100 个田字格、上千个 SVG path

四条必要的优化，别当成过度设计删掉：

- 每组 `content-visibility: auto` ＋ `contain-intrinsic-size` —— 屏幕外的组浏览器直接跳过
- 格子 `memo` 化 —— 否则每开一次浮层都要 reconcile 100 个田字格
- ⭐ **浮层开着时整面墙 `visibility: hidden`** —— 见下
- 跟随图用 `useMemo` 缓存 —— 它内容不变，而浮层**每轮循环都重渲染**

##### ⭐ 浮层开着时，墙必须停止绘制

上机反馈「点空白处关窗时，笔画动画会卡一下，过一会才关掉」。
换掉 forced reflow 之后**依然卡**，说明还有第二个来源：

```
半透明遮罩压在 100 个田字格上
  ＋ 笔画描画是 paint 属性的过渡（每帧重画被 clip 的粗描边）
  → 每一帧都要连着底下那一大片 SVG 一起重新合成
  → 主线程与合成器一直忙，点击事件被拖在后面
```

⚠️ 用 `visibility` 而不是卸载或 `display: none`：**布局与滚动位置都留着**，
关掉浮层她还在原来那一组。隐藏的子树也点不到，顺带免了误触。

#### 上机验收（2026-09-05）

三轮反馈，全部已修并确认：

```
✅ 等浮层入场动画放完（420ms）才动笔
   窗还在放大时就开写，起笔那一下会连着窗口一起缩放着划过去 —— 而那正是最要看清的
✅ 循环书写：写完停 1.1 秒，从头再来
   ⛔ 因此**没有「再写一遍」按钮** —— 它本来就在重写，而那个按钮占的
      正好是笔画该有的地方。她没看清就等下一遍，比先认出按钮再点它自然
✅ 笔顺跟随图在第一遍写完时浮现，之后**一直留着**
   每轮重写都收走的话，她的眼睛要跟着一个忽有忽无的东西跑
✅ 拼音与组词加粗 —— 这一屏仅有的两处文字，家长会照着念
⛔ 去掉喇叭与关闭按钮：点田字格就念这个字（不打断书写），点窗外关闭
```

⚠️ **「点外面能关」得有人告诉她一次**，这是刻意的取舍：
这一屏的全部注意力应该在那个字上。同时加了 Esc 关闭，
给键盘与读屏留一条退路（没有 ✕ 按钮之后，那是唯一的可达路径）。

#### ⛔ 重播时第一笔不会动 —— CSS transition 的合并陷阱

上机反馈「动画循环时，第一笔没有写的动画，直接出来了」。根因与笔顺数据无关：

```
第一笔的 delay 是 0
  → 「拉回隐藏（transition:none, offset=满）」和「推到 0」落在同一帧
  → 浏览器看到的起止值都是 0（上一轮结束时就是 0），判定没有变化
  → transition 不触发，笔画凭空出现
```

**首播不受影响**（那时初始值本来就是隐藏的），所以只在循环第二轮起暴露。

修法是在「重置」和「排期」之间**等两帧**（双 `requestAnimationFrame`），
让浏览器真的把隐藏状态画出去一次。

#### ⛔ 别用 `getComputedStyle` 去强制提交 —— 那会换来周期性卡顿

第一版修的时候用的是读一次 `getComputedStyle(el).strokeDashoffset`
来强制提交。它确实能修好第一笔，但**紧接着换来一个新毛病**：
上机反馈「点空白处关窗时，笔画动画会卡一下，过一会才关掉」。

根因是那行代码会触发**整个文档**的样式重算与布局，而这一页挂着
100 个田字格、上千个 path，循环每一轮都强制一次。

```
❌ getComputedStyle(el).strokeDashoffset   一次全文档 forced reflow
✅ 双 requestAnimationFrame                等的是同一件事，让浏览器按自己的节奏来
```

⚠️ **在重的页面上，「强制同步布局」是比它要解决的问题更贵的解法。**
这一页是全 App 最重的一屏，任何 forced reflow 都要先掂量一下。

⚠️ **同样的修复补进了 `generate-stroke-check.mjs`** —— 校验页每次重播有一模一样的
毛病（100 个字的 SVG，同样贵），只是核对笔顺时注意力在顺序上，没人注意到动画。
这正是「两边用同一套画法」该带来的好处：一处发现，两处都修。

#### ⚠️ 验证时踩的坑之一：`.fixed.inset-0` 选不到浮层

`AppShell` 里有一层 `pointer-events-none fixed inset-0 bg-deco` 的背景装饰，
**它在 DOM 里排在前面**。于是 `document.querySelector('.fixed.inset-0')` 恒定命中它：

- 检测「浮层开了没有」永远返回 true
- 往它上面派发 click 永远没反应（`pointer-events: none`）

结果一度判定「点遮罩关不掉」，差点去改一段本来就对的代码。
**验浮层要用 `[role="dialog"]`**，那是这一屏唯一属于它自己的标识。

#### ⚠️ 验证时踩的坑之二：程序化 `scrollIntoView` 会伪造出一个不存在的 bug

测试脚本里 `btn.scrollIntoView(); btn.click();` **写在同一个同步栈里**，
必然冻结页面；而真实用户滚动与点击隔着若干帧，实测（真实滚轮 ＋ 真实点击）
完全正常。差点照着这个假象去改渲染实现。

**验交互要用真实事件**，程序化调用能造出真实路径上根本不存在的时序。

### 3.1 ✅ 慢速重听（2026-09-04 完成）—— 学自每日英语听力的 8 档语速

拼音听辨那次（design/05 第 14 条）的解法是**全局**放慢到 -40%，
代价是所有孩子、所有时候都跟着变慢。每日英语听力的做法是把控制权交给用户。

#### ⭐⭐ 更正一：`playbackRate` 在这个项目里会变调，不能直接用

方案原本写的是「`audio.playbackRate = 0.75`，`preservesPitch` 不变调」。
**动手才发现前提错了**——那是 `<audio>` 元素的属性，而这个项目的片段播放走的是
Web Audio 的 `AudioBufferSourceNode`（为了裁静音和精确排期，那个选择本身是对的）：

| | 变速方式 | 变调？ |
|---|---|---|
| `<audio>` 元素 | `playbackRate` ＋ `preservesPitch` | ❌ 不变调 |
| **`AudioBufferSourceNode`** | `playbackRate` | ⚠️ **变调**——它就是重采样，等同放慢磁带 |

0.7 倍速音高降约 6 个半音，元音共振峰整体下移，`má` 会听成另一个音。
而慢速最该服务的恰恰是声调与 n/l 辨析——**为了听清楚把音教错，比听不清严重得多。**

所以慢速**单开一条 `<audio>` 路径**（`platform/slowSpeech.ts`），
正常速度那条 Web Audio 一行不动。

⛔ 反过来不成立：正常速度**不要**改用 `<audio>`——它没有音频时钟排不出稳定节奏，
拿的又是未裁剪的原始 mp3（每条尾部拖着 1.2 秒静音）。

#### ⭐ 触发方式：**只有长按**

中途试过「8 秒内再点一次就放慢」，想法是不用教她新手势。**2026-09-04 撤掉了**，
理由是它把**同一个动作绑了两种结果**：「再听一遍」是这个按钮最常用的用法，
而她想重听正常速度时会拿到慢速——那是误触发，不是便利。

```
按住 600ms → 慢一档     ⭐ 唯一入口
```

600 而不是通用的 500：六岁孩子按按钮本来就重、停留也久，
500 会把她普通的一次点击误判成长按。

代价是**需要有人告诉她一次**。这是明知的取舍：一个要专门做出来的动作，
换「常用动作永远得到她预期的结果」。

| `platform/useHoldToSlow.ts` | 长按放慢的通用 hook，返回摊到按钮上的事件属性 |
| `components/SpeakerButton.tsx` | 题干，触发时按钮闪一下 |
| `PinyinCard` · `HanziCard` · `LetterCard` · `PoemView` 的单句与译文 | 各自接上 hook |

题干那批是**全自动覆盖**的——所有题型都走 `SpeakerButton`。

⛔ 古诗的「读整首」**不加长按**：四句连着慢放太长，
而背诵时要反复磨的本来就是**某一句**。

#### ⚠️ 长按的三条，少一条就不工作

1. `onBeforeSpeak` 必须在 `pointerdown` 的**同步栈**里跑完——
   长按回调在 `setTimeout` 里，那时已经离开用户手势，iOS 会拒绝播放
2. 长按之后浏览器**仍会派发一次 `click`**，必须用 `consumeHold()` 吃掉，
   否则慢速刚响就被正常速度打断（`LetterCard` 还要靠它别把卡翻过去）
3. 按钮要带 `select-none touch-manipulation [-webkit-touch-callout:none]`，
   否则 iOS 长按会弹出系统菜单，把这一下整个抢走

⚠️ **只作用于题干与卡片，不作用于选项。** `choice_compare` 的四个选项一律排除，
理由同上：同一道题里必须同一档语速。选项不走 `SpeakerButton`，天然不受影响。

⚠️ 短文不涉及——它本来就没有语音（§2.1）。

#### ⚠️ 差点漏掉的坑：慢速通道没解锁时会静音

`unlockSlowSpeech()` 只挂在首页出口的 `unlockAllAudio` 上，
而孩子可以**整页刷新后直接停在拼音墙**——那时 `<audio>` 元素根本没建过，
第二次点击走进慢速分支就是一次**静默失败**（点了没声音）。
这比慢速不生效严重得多，直接撞「任何一条路径都不能通向静音」那条铁律。

补了两层：`isSlowReady()` 事前判断，以及 `playSlowUtterance` 返回
「有没有真的出声」——iOS 拒了 `play()` 时由 `say()` 用正常速度补一遍。

#### 已验证（浏览器实测，拦截三条播放路径计数）

```
普通点击 ×3         全部走 Web Audio，零次慢速                     ✅ 不误触发
长按一次            rate 0.7 · preservesPitch true · currentTime 0.25  ✅ seek 到人声起点
                    且同一轮 Web Audio 计数为 0                    ✅ 长按后那次 click 被吃掉
整页刷新停在拼音墙  点击照常走 Web Audio 出声                      ✅ 降级不静音
```

⭐ **验证本身踩了一个坑值得记**：程序化 `click()` 不构成用户激活，
Chrome 会拒掉 `<audio>.play()`，于是长按看起来「没生效」——
实际是**降级逻辑正常工作**把它接住了（走了正常速度）。
要验慢速本身，得先用一次**真实点击**建立 sticky user activation。
没意识到这一点的话，会去修一个根本不存在的 bug。

⚠️ **iPad 上还没验过。** `preservesPitch` 在 Safari 15.4 起支持（代码里连
`webkitPreservesPitch` 一起设了），但真机上是不是真的不变调、慢速听感如何，
只有耳朵能判——与拼音语速那次同一个道理。

## 4. ⏸ 暂缓：参与式讲解（洋葱学园）

洋葱的动画课 5~8 分钟，关键不在制作精良，在于**几乎每分钟都有一个问答交互节点**。
孩子不是看完再做题，是**边看边答**，视频停在那里等她。

这一条直接命中我们已经删掉的讲解模块（design/05 第 5 条）。
当时归因于「四步十格阵动画承载不了讲明白」，**只对了一半**：

```
真正的毛病是它是一个播放器 —— 四步里孩子没有一次需要动手
```

CLAUDE.md 那条猜想（「大概率不是动画，而是把讲解拆进题目本身的脚手架里」）
被洋葱的做法验证了。方向是对的。

### ⭐ 但暂缓，理由不是架构不够，是**没有验证手段**

架构上不难：追问就是「一道题拆成三道小题」，`sessionStore` 加一个分支，
TenFrame 是现成的。洋葱的成熟度堆在动画制作上，而追问不需要动画。

真正做不了的是：**追问脚本是内容工作量**——每个知识点一套，
而且必须真的能把她牵过去。写不好就是又一个她不理解的东西，和删掉的讲解同样下场。
而「这套追问有没有用」只能靠她在真机上被引导一次才知道，**单测一条都守不住**。

design/08 反复吃的就是这个亏（五个 SVG、`PetHome` 那个 bug，全是渲染出来才发现的）。
在没有验证手段的前提下做一块纯内容工作量，风险和收益对不上。

### ✅ 5% 成本的替代：脚手架按状态自动打开（2026-09-05 完成）

十格阵脚手架原先**只在难度 1 提供**，写死在生成器里。那有两处失灵：

```
她在难度 2 卡住   → 拿不到任何帮助，只能一直错到掌握度跌破 0.6 触发回退
她在难度 1 会了   → 十格阵还一直摆着，「逐步撤除」从来没真的发生过
```

#### ⭐ 关键取舍：是**叠加**，不是替换

方案原本写的是「把触发条件从『难度』**换成**『她的状态』」。**直接那样做会退化**：
难度 1 默认就不再有十格阵，她第一次遇到 `9 + 5` 是纯抽象的——比原先更糟。

所以难度仍然是**没有历史时的默认**，状态只做覆盖：

| 条件 | 结果 | |
|---|---|---|
| 听算题 | ❌ | 见下 |
| 连错 ≥2 | ✅ | 她卡住了，不论难度 |
| 连对 ≥2 | ❌ | 她会了，撤掉（**难度 1 也撤**） |
| 难度 1 | ✅ | 初次接触必须看得见 |
| 其余 | ❌ | 难度 2/3 靠心算 |

连错连对阈值同为 2，构成**带迟滞的闭环**：撤掉之后再连错两次它会回来，
不是永久剥夺。取 2 而不是 1 是因为一次错很可能是手滑，那时塞幅图进来
是把偶然当成不会。

#### ⛔ 听算题一律不挂脚手架

听算的题面本来就藏着（§2.2），再挂一幅图就成了**一张没有问题的画**。
她在听算上卡住，正确的补救是回到看算，不是给听算配图。

⚠️ 这条在 `shouldShowScaffold` 里**必须最先判**：听算题连错两次同样满足
「连错 ≥2」，顺序反了就会挂上。有一条测试专门锁这个顺序。

#### ⭐ 落点：脚手架从 `visual` 搬到 `scaffold`

这是整个改动的结构核心。两个字段的分工：

| | 含义 | 谁决定显示 |
|---|---|---|
| `visual` | 题目的一部分，**不画就无解**（尺子、钟面、条形图） | 没得选，必须画 |
| `scaffold` | 帮助，撤掉题目照样成立 | 由**她的状态**决定 |

生成器**无条件**产出 `scaffold`（算得出来就给），因为生成器是纯函数，
看不见她答错过几次。⛔ 别把它塞回 `visual`——那会让「难度 2 不该有脚手架」
这类规则重新长回生成器里。

| 文件 | 做什么 |
|---|---|
| `domain/types.ts` | `GeneratedItem.scaffold` |
| `domain/scheduler/shouldShowScaffold.ts` | 纯函数判据 ＋ 10 条测试 |
| `domain/generators/addWithCarry.ts` · `subWithBorrow.ts` | 无条件产出 `scaffold` |
| `stores/sessionStore.ts` | `kpStreaks`：开课时由 `masteryMap` 铺底，每题从 `recordAttempt` 就地更新 |
| `items/InputNumber.tsx` · `ItemRenderer.tsx` | `showScaffold` prop，缺省时按难度走默认 |

#### ⭐ 「下一题就挂上」在同一轮里真的成立

题目是**会话开始时一次性全生成**的（`buildSessionItems`），所以脚手架
不能在生成时定死——否则「连错 2 次」要等下一轮才生效，而一轮只有 10 题、
做完还得她主动再来一轮，等于可能永远等不到。

`AttemptOutcome.mastery` 正好带回更新后的 `consecutiveWrong / consecutiveCorrect`，
会话内即时判定**零额外查库**。

⚠️ `kpStreaks` 开课时用她**进来之前**的连错连对铺底：上一轮就卡着的知识点，
这一轮第一题就该带着脚手架，而不是让她重新错两次换取。

#### ⚠️ 差点静默失效的一条测试

`itemTemplates.test.ts` 那条「听算题不带配图」查的是 `item.visual`。
脚手架搬到 `scaffold` 之后，**它就查不到脚手架了**——而这恰恰是这次新增的红线。
已扩成两个字段都查。

> 这与 §2.2 那次「声明与实际一致那条只查 `M2-` 开头的模板」是同一个形状：
> **搬动字段时，原有断言会安静地不再覆盖它想覆盖的东西。**

#### 已验证（临时预览页，真生成器 ＋ 真 ItemRenderer，验完即删）

```
① 难度1 无历史        十格阵在（9+2）                    ✅ 回归没丢
② 难度1 连对2次       撤掉，scaffold 数据仍在             ✅ 逐步撤除生效
③ 难度3 连错2次       挂上，四个选项完整可见未被挤下屏      ✅
④ 难度3 无历史        无                                 ✅
⑤ 听算 连错5次        只有声波占位，无图                  ✅ 红线守住

```

⚠️ **iPad 真机未验**，但挤压风险实际不存在：③ 与「难度 1 有脚手架」是
同一个 44px 的 `TenFrame`，那个布局早已上机跑过——不是新布局，只是新时机。

⚠️ **它没有顺手解开风险 3（M5/M6 挂听算）**。反而多一种冲突态，
由「听算一律不挂脚手架」挡掉了。要把听算铺到 M5/M6 仍是独立的一件事。

## 6. ⭐⭐ 笔顺验收方案：验部件，不是验字

这是笔顺模块唯一真正的未知数，单独成节。

### 6.1 先修正一个事实

`makemeahanzi`（`hanzi-writer-data` 的上游）**明确以大陆（PRC）笔顺为目标**，
项目文档写着这一点，并说明日本、台湾用不同笔顺、他们没精力做。

容易搞混的是：它的**字形轮廓**来自 Arphic 的台湾字体，但**笔顺标准**是 PRC。
两者是两件事。**所以风险比「台湾来源」这个第一印象低。**

但不是零：笔顺是从字体数据**提取**的，不是人工逐字录入；
项目自述提到的人工校验主要覆盖繁体字，简体那部分的验证情况没有说明。
**目标对了，不保证每个字都对。**

### 6.2 ⭐ 核心：验收单位是部件

**笔顺分歧不是随机撒在 300 个字里的，它集中在特定部件上。**
「忄」在快、慢、情、怕、忙里的笔顺完全一样——验一次「忄」，等于验了所有含忄的字。

```
验 300 个字   → 300 次判断，每次都需要专业知识
验十几个部件  → 十几次对照，每次都能在孩子的语文书上翻到
```

⭐ **一年级课本的生字表本身就带笔顺**，而识字 300 的字表本来就对着教材来。
存疑的部件直接翻书对——比任何在线资源都准，**因为教材就是她要学的那个标准**。

### 6.3 分层漏斗

| 层 | 做什么 | 状态 |
|---|---|---|
| ① 笔画数 | 与权威笔画数比对 | ⏸ 缺独立数据源，见下 |
| ② 笔画类型序列 | 第二源比对（横竖撇捺折） | ❌ 做不了，见下 |
| ③ **同部件几何一致性** | 同一偏旁在不同字里的笔顺必须一样，对不上就是数据错 | ✅ **自动，零外部依赖** |
| ④ **风险分级筛查** | 两岸分歧 · 简化字特有 · 撞硬规则 → 进人工队列 | ✅ **主力** |
| ⑤ 人工 | 只看 ③④ 筛出来的，对着课本比**序号顺序** | ✅ 52 个 |

⚠️ **② 层查证后确认做不了**：`cnchar` 的绘制插件就是拿 `hanzi-writer` 的数据驱动的，
拿它当第二源等于自己跟自己比。而**没有找到公开、机读、独立的大陆笔顺编号数据集**
（GF 0023-2020《通用规范汉字笔顺规范》是出版物，不是数据集）。

① 层同理待定——需要独立的权威笔画数来源才能自动化。
⚠️ 这两层缺失的后果只是人工队列长一点，**不影响 ③④⑤ 成立**。

#### ⭐ ③ 层是这套方案唯一不需要外部数据源的自动判据

含同一偏旁的字，那个偏旁的笔顺必须完全一样——**对不上说明数据自身矛盾，
不需要懂笔顺也能断定**。落点是 `PART_GROUPS`（女旁 5 字、口旁、犭旁、鸟旁……）。

⚠️ **比的是每笔首末点的方向角，不是推导出的笔画类型。**
第一版比类型，误报了 3 组（女旁 5 字、口旁、鸟旁全被判成不一致）——
原因是点数少的笔画（「提」只有 4~5 个采样点）首末两小段就是全部，
末端一点点上翘就把「转折判定」推过了阈值。

改比角度后全部通过：女旁 5 个字的三笔角度是 −77~−79° / −115~−120° / 8~11°，
几何上高度一致。**笔画分类有边界抖动，角度没有。**

> ⭐ 这一条本身就是 §6.5 的实例：**AI 写的自动判据，自己也要验一遍。**
> 那 3 条误报如果直接当成「发现了数据错误」报出去，接下来就是照着不存在的问题去改数据。

### 6.4 ⭐ 兜底：验不了的字，就不给笔顺

这条比上面所有层都重要：**笔顺是可选功能，不是必需功能。**

数据里加 `strokeOrderVerified`。没通过校验的字只显示田字格和字形，不演示笔顺。
300 个字里有 280 个能演示已经完全够用，
而这个兜底把整个模块的风险从「可能教错」降到「有些字没有」。

⛔ **绝不「存疑但先放着，以后再说」**——那正是教错的那条路径，
和古诗多音字「此处读的正是最常用音」是同一个念头。

### 6.5 分寸：AI 不当最终判据

写校验脚本、整理分歧部件清单、生成对比页、挂权威参考链接——这些 AI 能做。

**但不该由 AI 判定某个字的笔顺对不对。** 对具体字笔顺的记忆不可靠，
这正是「看起来会、但可能错」最典型的场景——
和 TTS 念古诗时主动往古音靠是同一类问题：不是不会，
是**会得不够可靠，而错了没人发现**。

#### ⭐ 页面的关键设计：每笔起点标序号，而不是只给动画

核对笔顺不该靠盯动画。标了序号之后，语文书的生字表摊在旁边，**一眼比完一个字**。
动画退居为「看不出这一笔是哪一笔」时的补充。

⚠️ 序号**必须做碰撞避让**：「日」「月」「四」「目」这类字头两笔起点几乎重合
（竖与横折都从左上角起笔），直接摆在起点上两个圈会叠成一个，
而那恰恰是最需要看清的地方。做法是沿「起笔的来时方向」外推，撞了就换垂直方向，
**全撞时取离已放置序号最远的那个**——这一条是渲染出来才发现的，

按笔长成比例的节奏都正常。**引库与否在丝滑度上没有区别这个判断，到此是验过的。**

⛔ **`VERIFIED_VOLUMES` 仍然只有 `vol1`**，写字墙上还是只有第一辑那 100 个字。
核对通过后才把 `vol2`/`vol3` 加进去、重跑 `npm run stroke:data`。
理由见 §6.4 与 §6.5：AI 不当笔顺的最终判据，而「存疑但先放着」正是教错的那条路径。

#### ⭐⭐ 更正 §8：「同一套部件清单对第二、三辑同样适用」是**错的**

第二辑第一次跑出来是「**需要人工核对 0 个 · 同部件一致性全部通过**」——
看着像内容很干净，实际是**筛子一个都没网到**：

```
DIVERGENT / SIMPLIFIED / RULE_RISK   三张表里全是第一辑的字
PART_GROUPS                          chars 全是第一辑的字，每组凑不满 2 个 → 全部 continue
```

三层筛查在第二辑上**全部空转**，而输出和「真的通过」长得一模一样。

已补两件事：

1. **扩充四张表到二、三辑**。新增 17 组部件（忄氵艹虫饣衤足讠纟钅目日穴竹宀冫雨），
   ⭐ 其中「忄」正是 §6.2 举的例子——验一次它等于验了所有含忄的字。
   人工清单按**部件代表字**列（讠·纟·钅·饣 各留一个），
   其余同旁的字交给 ③ 层自动兜住，这样清单才压得住规模（38 / 33，与第一辑的 52 同量级）。
2. ⭐ **让空转不再伪装成通过**。脚本现在打印实际比过的组数，
   一组都没比上时明说「不是通过」；必看清单为空时也警告。

> **教训**：一个只会输出「通过」的检查，和没有检查是一回事。
> 加新数据时要先确认**筛子够得着它**——这和 §2.2 那次「断言只查 `M2-` 开头的模板」、
> 以及短文那次「听算不带配图只查了 `visual`」是同一个形状，一个月内第三次。

## 7. ⛔ 明确不抄的，以及为什么

| 来源 | 机制 | 为什么不抄 |
|---|---|---|
| Duolingo | **streak 连续天数** / 断签提醒 | 正面撞宠物红线第 2 条。断掉 streak 产生的是负罪感和回避——而「我有点想你」这句话存在的全部理由就是避开它 |
| 洋葱 · 小猿 | 排位赛、段位、在线 PK | 同「三只宠物之间绝不比较」的理由；且纯本地无网络，硬约束排除 |
| 小猿口算 | 限时倒计时 | 一年级练的是**理解**不是速度。计时会把答错的原因从「不会」变成「来不及」，而后者在掌握度里长得和前者一模一样 |
| 洪恩识字 | 每个字配大段互动小游戏 | ⭐ 家长实测吐槽最集中的一条：「游戏环节占比过大，孩子在上面过度停留」，学到 200 字后**识字效率反而下降** |
| 多家 | 抽卡 / 开箱 / 随机奖励 | 撞宠物红线第 6 条：成长必须确定、努力可预期 |
| Duolingo ABC | 语音识别跟读打分 | iOS Safari 的 Web Speech 识别不可靠且要联网，撞「纯本地不上云」硬约束 |
| 小猿口算 | 拍照批改 | 需要服务端 OCR，同上 |

### ⭐ 洪恩那条教训值得单独记

家长的实测轨迹是：**付费后孩子进入近乎疯狂的阶段 → 早上起床就要玩 →
学到 200 字后效率下降。**

看起来是成功（粘性极高），实际是失败——**孩子粘住的是游戏，不是识字。**

我们的宠物小屋、商店、零食动画在结构上是同一类东西。
现在的分寸是对的（小屋不产出学习行为、零食只是花掉星星的回报），
但**扩充它们之前要先问一句：这一步是让她更愿意学，还是让她更愿意玩这个 App。**
两者在留存数据上长得一样，在教学效果上正好相反。

#### 短文加内容：新开一辑，或往当前辑末尾追加

与识字墙、诗单同一条规矩：**不重排辑、不重排辑内顺序**。

**三辑已齐（2026-09-05），共 24 篇**：

```
第一辑 8 篇  只有 100 字，动词只有「看听说走坐站飞吃来去开关」
             → 句子必然短而具体，那正是她这个阶段读得动的东西
第二辑 8 篇  200 字，多出洗穿跑跳游笑唱玩想找拿做用写读画学睡停骑
             → 第一次写得出「一天里发生了什么」这种有先后的故事
第三辑 8 篇  300 字，⭐ 到这里才有「是」「有」「不」「很」
             → 句子第一次能判断、能否定，写得出说明性的段落
```

⚠️ **第三辑仍然写不了寓言**：「乌鸦」「守株」「龟兔」「拔苗」这些关键词
一个都不在 300 字里。硬凑出来的不是寓言，所以 24 篇的 `source` 全是「自己写的」。
⛔ 别为了让出处栏好看就标成「寓言」——那是在骗自己。
真要放寓言得等第四辑（识字加辑之后）。

⚠️ 加辑只要往 `STORY_VOLUMES` 后面追加，UI 自动多一个分辑按钮
（`StoryLibrary` 在只有一辑时刻意不显示切换条——一个孤零零的按钮点了没变化，
反而像坏了）。⛔ 短文 id 不能以 `vol` 开头，理由同诗单。

⚠️ **不要为短文生成任何语音**。`voiceManifest` 与 `npm run voices` 一行都不用改——
它复用识字墙已有的单字片段，这正是这个模块最大的好处。
