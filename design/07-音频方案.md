# 音频方案

> 音效 + 语音。**运行时零网络**：所有音频随包发布，离线可用。
> 相关代码：`platform/audio.ts` · `platform/speech.ts` · `domain/speech.ts` · `data/seed/voiceManifest.ts`

---

## 0. 两个独立的问题

| | 音效（SFX） | 语音（Voice） |
|---|---|---|
| 是什么 | 点击、答对、答错、升级的提示音 | 题干、反馈语、宠物台词的朗读 |
| 之前 | **完全没有** | Web Speech 实时合成 |
| 问题 | 每次交互只有视觉反馈，缺一半 | **音色差**，且拼音必须预录 |
| 现在 | 6 个脚本合成的 WAV | 预生成 mp3 片段拼接，TTS 兜底 |

---

## 1. 音效

### 1.1 为什么是脚本合成而不是找素材

免费音效库的授权条款五花八门，而「柔和、不刺耳、适合一年级」这个要求很难靠搜索命中。
这几个音本质上就是几条正弦波加包络，自己算反而更可控——
想让答错音再柔一点，改一个数字重跑 `npm run sfx` 就行。

输出 WAV 而非 MP3：六个音总共约 100KB，省下 MP3 编码器的复杂度，iOS Safari 对 WAV 支持良好。

> **要换成真实音效素材时**：把同名文件丢进 `public/audio/sfx/` 覆盖即可，代码一行不用改。

### 1.2 六个音

| key | 用途 | 设计要点 |
|---|---|---|
| `tap` | 所有 `BigButton` 点击 | 极短极轻，只确认「点到了」，不能有存在感 |
| `place` | 拖拽卡片落进槽 | 闷一点的短音，确认「吸住了」 |
| `correct` | 答对 | 上行大三度，明亮但不夸张 |
| `wrong` | 答错 | ⭐ **下行小三度 + 40ms 慢起音**，音量压到六成 |
| `complete` | 一轮完成 | 两个音收尾，比升级克制 |
| `levelUp` | 宠物升级/变身 | C 大调琶音，全 App 最「大」的音 |

> ⭐ **`wrong` 是产品红线所在**（CLAUDE.md「答错反馈要温和」）。
> 慢起音去掉了「咔」的攻击感，听起来像一声轻轻的「嗯…」而不是警报；
> 音量刻意低于 `correct`——**答错的反馈不该比答对更响亮**，那是在放大挫败感。

### 1.3 接线位置

```
BigButton.onClick        → tap        全 App 的按钮都走它，一处接线全覆盖
usePlacement.place()     → place      拖与点两条通道都经过它
Feedback（进入反馈态）    → correct / wrong
SessionSummary（挂载）   → levelUp 有升级时 / complete 否则
```

⚠️ 选项按钮**不接** `tap`：它点下去几十毫秒后就是 `correct`/`wrong`，两个音会糊在一起。

## 2. 语音

### 2.1 为什么弃用实时 TTS

1. **音色差** —— Web Speech 在 Windows 上用的是老式 SAPI 音色，实际听感不能接受
2. **拼音必须预录** —— design/03 §9 风险清单早就写明：
   拼音音节靠运行时 TTS 会发音不准，**误导孩子**，这是内容正确性问题不是体验问题
3. **不确定性** —— 同一句话在不同设备、不同系统版本上音色不同，且随系统更新变化

### 2.2 核心思路：题干是拼出来的，语音也拼出来

数学题运行时生成，题面无穷无尽，不可能为每道题预录一条音频。
但它们都由极小的词汇表拼成：**0~20 的数字 + 几十个固定短语**。

于是把一句话表示成**片段 key 的数组**：

```ts
// 9 + 5 = ?
{ parts: ['num.9', 'op.plus', 'num.5', 'phrase.equalsWhat'],
  fallbackText: '9 加 5 等于几' }
```

无穷多的题目只需要**几十个音频文件**，而且发音完全稳定。

### 2.3 ⭐⭐ 必须裁静音 —— 否则一句话要念 7 秒

Edge TTS 的输出有**固定最小长度**。实测每个短片段都是 **1.78 秒**，
而其中真正的人声只有 0.24~0.64 秒，**尾部一律拖着约 1.2 秒静音**：

| 片段 | 文件时长 | 人声区间 | 尾部静音 |
|---|---|---|---|
| `num.5`（五） | 1.78s | 0.21–0.57s | 1.21s |
| `op.plus`（加） | 1.78s | 0.22–0.46s | 1.32s |
| `phrase.equalsWhat`（等于几） | 1.87s | 0.21–0.85s | 1.02s |

于是「9 加 5 等于几」按原样播放要 **7.3 秒**，其中 5.8 秒是死气——
孩子实测反馈「读得很慢」，根因就在这里。

**修法**：解码后按能量扫描定位人声区间，裁掉前后静音再播。同一句降到 **2.4 秒**。

```
裁剪前  ■□□□□ ■□□□□ ■□□□□ ■□□□□   7.3s（■人声 □静音）
裁剪后  ■ ■ ■ ■                      2.4s
```

⚠️ 裁剪保留前后各 30ms 余量：塞擦音（z c s）起音很轻，
卡着门限切会把字头削掉，听成另一个音。

### 2.4 播放走 Web Audio，不用 Howler

音效用 Howler（即发即忘，正合适），**语音必须用 Web Audio**：

1. 要裁静音——Howler 不做这件事
2. 要在音频时钟上**一次性排期**整句。边放边解码会在片段之间插进不确定的加载延迟，
   听感就是「一顿一顿的」
3. 原来用 Howler 按需加载，首次用到某片段时它还没加载完，
   而新的朗读会调 `stop()` 取消排队播放，于是**低频片段整个被吞掉**——
   孩子实测反馈「有的数字没读出来，比如 15」，正是这个原因。
   现在解锁时预热数字与运算词（约 27 个、300KB），播放时一定是就绪状态。

### 2.5 三条播放路径 —— ⭐ 绝不能通向静音

```
片段齐全   → 按顺序播放预生成 mp3      ← 目标状态：音色稳定、离线、零延迟
缺任一片段 → 整句降级为实时 TTS        ← 音色不一致，但听得见
无 TTS 支持 → 静默失败，但不抛错        ← 页面不能崩
```

孩子不识字，题干读不出来 = **这道题她做不了**。
宁可某一句音色不一致，也绝不能让她盯着一道读不出来的题。

> ⚠️ 缺片段时是**整句**走 TTS，不是「有的片段有的 TTS」。
> 混着播会得到「9 加（真人声）…（机器声）等于几」，比全程机器声更难听。

### ⭐ 2.5b 昵称：唯一一组「内容由家长决定」的片段

App 用孩子的昵称称呼她（「小恩宝，今天想学点什么？」「小恩宝，太棒了」）。
昵称在家长区随时可改，而预生成音频是**构建期**的事——
运行时不可能凭空造出任意三个字的真人音色片段。

于是复用上面那条降级规则，不需要改播放器：

```
昵称在 nicknamePresets.ts 里 → 整句都是片段    「小恩宝，太棒了」全程少女声
昵称不在清单里               → 整句降级 TTS    音色变了，但名字叫得出来
没设置昵称                   → 退回原文案       「太棒了」
```

选「整句 TTS」而不是「语音里干脆不叫名字」：孩子不识字，
名字写在屏幕上等于没写，**只有念出来才算数**。宁可换音色也要叫对人。

> ⚠️ **`addressed()` 有一条容易踩的坑**：后半句没有任何片段时
> （宠物台词这类还没纳入清单的内容），不能只把昵称片段放进 `parts`——
> `say()` 会认为「片段齐全」而**只念出一个名字**，后半句连同兜底文本一起消失。
> 见 `domain/encourage/addressed.ts` 与它的测试。

拼装逻辑在 `domain/encourage/`（纯函数）。

⭐ **昵称片段按说话者音色各生成一份**（2026-08 起）：旁白一份（`name.xiaoenbao`）
+ 三只伙伴各一份（`name.penguinXiaoenbao` / `name.dragonXiaoenbao` / `name.pandaXiaoenbao`）。
宠物有了专属音色之后，「小恩宝，我有点想你」整句都得是那只宠物的声音——
少女声的名字接男童声的台词就是一句话里两个人在说。
说话者由台词片段 key 自动判定（`domain/encourage/petSpeaker.ts`），
调用方不用传；变体 key 的构造规则与生成脚本 `loadNicknames()` 逐字一致，
`voiceManifest.test.ts` 有变体齐全性用例兜底。

同一套机制还用在另外三处：

| 片段 | 内容 | 没有片段时 |
|---|---|---|
| `pet.*` | 六只伙伴的**默认**名字（团团/墨墨/波波 · 喵喵/小白/咩咩） | 不会缺 |
| `petname.*` | 起名候选池（`petNamePresets.ts`）。⭐ 起名已改成**从预录名单点选**（PetNamePicker），改名后升级播报不再降级 | 旧档案键盘起的名 → 整句 TTS |
| `petline.*` | 71 句宠物台词，写在 `pets.ts` 的 `PetLine` 里 | 不会缺，`pets.test.ts` 逐句校验 |
| `phrase.good*` | 早/中/下午/晚四句时段问候 | 不会缺 |
| `shop.*` | 商店商品名（家具 / 零食 / 现实券） | 不会缺；现实券**只能从预设里挑**正是为此 |

⭐ 宠物台词之所以值得全部预生成，是因为它们现在出现在**每一次答对**的反馈里
（鼓励语池 = 通用 5 句 + 本轮伙伴的 4 句）——那是全 App 最不能掉音色的位置。

⭐ **买到东西的庆祝语也是拼出来的**（2026-08 起）。原先它走 `plain(text)`
整句实时 TTS，孩子实测直接听出来了：「『谢谢你』的人声和别处不一样」。
现在拆成「商品名片段 + 后半句片段」，后半句只有三条：

| 情况 | 片段 | 念什么 |
|---|---|---|
| 家具 | `phrase.itsYours` | 是你的啦 |
| 零食 | `phrase.feastThanks` | 大家一起吃，谢谢你 |
| 现实券待兑现 | `phrase.toldParents` | 已经告诉爸爸妈妈啦 |

逻辑在 `domain/economy/celebrationLine.ts`，屏幕文本与朗读内容逐字一致
由 `celebrationLine.test.ts` 强制校验。商品名缺片段时整句降级 TTS，
**绝不半片段半 TTS**——与昵称同一条铁律。

> 这条最值得记住的不是修法，而是**六岁孩子能听出音色不一致**。
> 「反正只有一句，先用 TTS 顶着」这个念头以后别再有了。

### ⭐ 2.5c 一次只说一句话

`say()` 是**打断式**的，而 React 先跑子组件的 effect、再跑父组件的。
于是「小结页同时有升级横幅」时，横幅刚念出「团团变身啦」就被小结语掐掉——
这个 bug 存在了很久，因为它的表现只是「好像没听见」。

规则：**同一屏里绝不能有两个组件各自调 `say()`**。
要加新播报就往已有的那句话里拼（`summaryLine(nickname, stats, levelUp)`），
而不是新开一个 effect。

家长留言是唯一的例外场景，但它由**点击**触发，不与任何自动播报同时发生。

### ⭐ 2.5d 预取策略 —— 「点了就响」靠两层保障

**网络层**：语音以 **8 个 `.bin` 语音包**的形式进 Workbox 预缓存，
装好后 fetch 是本地缓存读取。⚠️ `npm run dev` 没有 Service Worker，
局域网调试听到的加载延迟**在线上不存在**；验证请用 `npm run preview`。

### ⭐⭐ 为什么打包：请求数才是首装的瓶颈，不是字节数

实测反馈「首次打开等了好几分钟」。根因不是体积——**12.6MB 一点也不大**，
而是它被拆成了 **764 个平均 15KB 的小文件**：时间几乎全花在
「发请求、等响应」上，浏览器并发只有 6 路，GitHub Pages 从国内访问
又有 300~500ms 延迟，乘起来就是几分钟。

`scripts/bundle-voices.mjs` 把 mp3 按内容域拼成 1~3MB 的包
（core×2 / english / hanzi×3 / pinyin / poem×4 / pet），
**预缓存条目从几百条降到几十条**，同样的字节按带宽跑满。

> 包数随内容长：识字扩到 300 字后 `hanzi` 自己就占了 3 个包，
> 古诗扩到 60 首后 `poem` 占了 4 个（诗句是整句，单条比识字卡长得多）。
> 现为 **1325 条片段 / 12 个包 / 26.5MB**。
>
> 也会随内容**变短**：删掉「看讲解」模块后 `explain` 那个包（15 条 / 479KB）
> 整个消失——语音包的组是由 key 前缀推出来的，没有片段的组不会留下空包。
> 升年级过场（`ceremony.*` 2 条）与往届伙伴台词（`petline.*Archived*` 9 条）
> 补完后是 **1340 条 / 13 个包 / 27.0MB**（2026-08-27）。
> ⚠️ 封版指的是**年级上限**（中文片段只做到二年级），不是「一条都不能再加」——
> 一二年级范围内该有的话没说完，那不叫封版，那叫少做。
> 分包是按体积上限自动切的，加内容不需要动打包脚本——
> 但**索引文件要跟着提交**（见下表）。
>
> ⭐ **这就是语音包最终的样子。** CLAUDE.md 红线「语音包到二年级为止」，
> 二年级已于 2026-08-26 做完并封版，三年级起不再生成任何中文片段
> （英语 `en.*` 发音除外）。

```
mp3 原样首尾相接 → 索引记 [包名, 偏移, 长度]
运行时 buffer.slice(off, off+len) 切出来的**就是一个完整 mp3**，直接喂 decodeAudioData
```

不需要任何容器格式或重编码——这是这套方案成立的关键。

| 事项 | 说明 |
|---|---|
| 产物 | `public/audio/bundles/*.bin`（**不进 git**，`npm run build` 每次重新生成） |
| 索引 | `src/data/seed/voiceBundleIndex.ts`（**要提交**，运行时与测试都读它） |
| 分卷 | 上限 3MB，必须小于 Workbox 的 `maximumFileSizeToCacheInBytes`（设为 4MB）——**超了会被静默排除出预缓存** |
| 兜底 | 包缺失/损坏时回退单文件 `audio/voice/<key>.mp3`（mp3 仍在 dist 里，只是不预缓存） |
| 校验 | `voiceBundleIndex.test.ts`：清单里每条都必须在包里。漏的那条离线会哑 |

⚠️ **mp3 刻意排除出 `globPatterns`**：留着等于把同样的 12.6MB 下两遍。
⚠️ 加了新片段必须重新打包（`npm run voices` 与 `npm run build` 都会自动跑）。

**⭐ 启动自检门（`VoiceCacheGate`）**：预缓存是 SW 安装期一次性的，
装到一半断网或更新没下完，缺的片段不会自己补上——表现是某些句子静默降级成机器音。
所以每次启动先审计缓存（齐全时几百毫秒、零渲染），缺了就盖一层进度弹窗：

```
SW 已接管  → 主动逐条 fetch 缺失文件；vite.config 的 audio-repair
             CacheFirst 运行时路由会顺手缓存——fetch 本身就是补录
首次打开   → SW 还没接管页面，fetch 缓存不下来；轮询预缓存进度直到 SW 装完
             ⚠️ 首屏预热也由这道门在放行后才发起——预热会连带下载整个语音包，
             提前发起会让同一个包被「页面预取」与「SW 预缓存」各下一遍
断网       → 一轮毫无进展就提示「检查网络」，并给一个小字的「先跳过」逃生口：
             本次会话放行（缺的句子走 TTS 兜底），后台补录不停，联网即静默补齐
补齐       → 弹窗自动消失，App 放行
```

> ⚠️ 「先跳过」只在 stalled 时出现——正常下载中不给。
> 门的意义就是补齐，逃生口不能比「等一分钟」更显眼。

家长区仍保留手动「语音资源自检」（`platform/voiceCacheAudit.ts`），用于更新后主动核对。

**解码层**：`say()` 会等片段 fetch + 解码完才出声，等到点击才开始就是「按了没反应」。
所以按「马上要用」的范围分批预取（`prefetchClips` 可在任何手势之前调用，
iOS 只禁播放不禁解码）：

| 时机 | 取什么 | 在哪 |
|---|---|---|
| App 挂载 | 数字 · 运算词 · 鼓励语 · 问候 · 昵称（含伙伴音色变体）· **全部宠物台词** | `WARMUP_CLIPS` |
| 进学习会话 | ⭐ **本轮全部题目的题干 + 选项片段**；答错引导语 · 小结 · 升级组装件（`SESSION_CLIPS`） | `LearningSession` |
| 进摸底 | 探险反馈语与终点语 | `Assessment` |
| 进内容页 | 该页全部片段 | 各 Wall / PoemView / Explainer |

⚠️ 刻意**不做**「启动时全量解码」：764 条解码后的 PCM 是上百 MB 内存。
预缓存管网络、按需分批管解码，两层合起来就是零感知延迟。

### ⭐ 2.5e 答错那句：答案念不出来时**只说安慰语**

答错反馈是「（伙伴安慰），答案是 X」。前两截（`petline.*` / `phrase.answerIs`）
永远是片段，唯独答案那半截要看题目给不给得出——给不出就整句降级为实时 TTS。

而这条降级路径曾经吃掉**全库 40%**：4878 道采样题里 1926 道、86 个知识点。
根因不是没有片段（拼音、英语的答案片段全是现成的，题干正在用同一个 key），
而是没人负责说「这道题的答案怎么念」：`ItemOption.ttsParts` 的语义是
「**点这个选项**听什么」，而听力题的选项一律不可点读（点一遍等于报答案），
于是那个字段一直空着，答案就一路降级下去了。

因此答案语音单立一个字段 `GeneratedItem.answerSpeech`，三种取值三种播法
（推导在 `domain/resolveAnswerSpeech.ts`，全库由 `voiceManifest.test.ts` 逐条模板校验）：

```
parts 非空   → 整句拼片段     「（安慰），答案是 苹果」全程预生成音色
parts = []   → 只说安慰语      答案念不出来，不接「答案是」那半句
undefined    → 整句降级 TTS    兜底，⛔ 不允许新增（测试会拦）
```

**「不念」不是妥协，是正确答案**。这三类题硬念都比不念糟：

| 题 | 答案长什么样 | 念了会怎样 |
|---|---|---|
| 轴对称 / 平移旋转 / 观察物体 / 认角 | `grid:5:00.11.21.30` | TTS 一个字符一个字符念出来 |
| j q x 去两点 · 标调位置 | `ju` / `hǎo` | 四个选项读音一模一样，念了是句废话；裸拼音还会读错声调 |
| 记忆翻牌 | `全部配对成功` | 那不是答案，是「你刚才没做到的事」 |

代价为零：正确选项本来就会在屏幕上高亮（`OptionButton` 的 `reveal-correct`），
**图案类的还会在反馈里画出来**——图案选项的 `text` 存的就是画图用的 key，
以前那串 key 直接显示给孩子看，现在换成 `MathShape`（错题卡同理）。

⚠️ `parts = []` 时不能拿 `phrase.lookAgain` 顶上：那条片段念的是
「再看看，**答案是**」，后面不接答案就成了半句话。没有伙伴时走 TTS 说「再看看」。

⭐ 一条反直觉但必须守的规矩：**英语听音题的答案念英语，点选项念中文**。
题没答完时念英文等于报答案（`faceOptions.ts`），答完之后正相反——
她刚才没听出来的就是那个音，这时再念一遍才是补救，屏幕上同时高亮着 🍎。
兜底文本用中文释义：片段万一缺失会走中文 TTS，那时念 `apple` 是在教错发音。

⭐ 声母韵母题的答案念**呼读音**（g→「哥」、ai→「哀」），映射在
`domain/pinyinCallName.ts`，复用音节表现成的载体字片段，零新增音频。
`ong` 没有干净载体，那一档宁可不念——念一个 TTS 猜出来的声调是在教错。

### 2.6 片段清单是唯一事实源

`data/seed/voiceManifest.ts` 同时被**生成脚本**和**运行时**读取。

如果脚本自己维护一份「要生成哪些音频」的列表，它迟早和代码实际用到的片段对不上：
多生成的是死文件，少生成的是**静音**。共用一份清单 +
`voiceManifest.test.ts` 校验「代码里用到的片段都在清单里」，这类漂移不可能发生。

> ⭐ **四个声部一耳朵可辨**：男童 / 青年男 / 温暖女 / 少女，
> 孩子不看屏幕也知道是哪只伙伴在说话。宠物音色只用于**它自己的台词**

> ⚠️ **`penguin` / `dragon` / `panda` 这三个词现在指「声部」，不是物种。**
> 二年级换了物种但沿用同一批声音（`petline.dragonG2Greet0` 是萨摩耶小白的台词），
> 数学的伙伴永远是男童声——这条线索不该每升一个年级就重置一次。

> 也学不对的音——这与拼音「裸拼音会读错声调」是同一类问题，
> 而发音教错比没有声音严重得多。脚本按前缀切音色，
> 一个 worker 绑定一个音色（`setMetadata` 是连接级设置，中途换不了）。

### ⭐⭐ 拼音为什么单独一套：孤立单字的声调会读飘

人工复听（`npm run pinyin:check`）报回 18 个发音有问题的音节，
其中 **11 个是一声**（`pō mō kē hē wū āo ōu yē ēn wēn āng`），
另有三声的 `nǐ`。模式很清楚：**全都是孤立的单个汉字**。

根因是中文 TTS 念孤立单字时缺少语境，韵律模型按「一整句」处理，
句末天然带降调倾向，把一声的高平调（55）拖成下降；
三声在快语速下则被压成「半三声」，孩子听到的不是课本上那个音。

两条对策，都只作用于 `pinyin.*`：

1. **换标准播音音色** —— 少女声念题干很好，念孤立单字不够稳。
   播音腔在别处是缺点，在「教这个音该怎么念」上恰恰是优点。
2. **`-30%` 语速 + `+0%` 音调** —— 慢让声调走完；⚠️ 而音高偏移是可疑因素：
   中文声调本就是**相对音高的变化**，TTS 的整体升调并非简单平移，
   一声（本就在音域高处）被抬高后容易撞顶变形。
   别处的 `+5%` 只影响亲切感，这里影响对错。

> ⚠️ 台账 `.spoken-text.json` 现在同时记录**生成参数指纹**。
> 早先只比对「念的文本」，于是改音色/语速**不会**触发重生成——
> 与当初「改了载体字音频却不更新」是同一类坑，那次是靠人肉发现的。

第一轮复听后 18 → 4 条。

### 最后几个：尾随逗号

剩下 `wū`（屋，两处 key）· `ēn`（恩）· `é`（鹅）怎么调参数都读不稳。
共同点是**这几个字几乎不单独使用**，TTS 训练数据里缺少它们作为独立句子的样本。

对策是给它们补一个**尾随逗号**（`scripts/generate-voices.mjs` 的 `TAIL_FIX_KEYS`）：
那个字不再位于句末，韵律模型就不给它加收尾的降调。多出来的停顿是静音，听不出来。

```
⚠️ 刻意只对清单里的几个用，不全局开。
   换音色 + 放慢之后 102 个拼音已有 98 个读准，
   全局加逗号等于把那 98 个重新赌一次（神经 TTS 未必每次输出一致）。
   复听发现新的读不准，往 TAIL_FIX_KEYS 里加即可，签名会自动触发重生成。
```

**已知的死角，只能录真人音频**（`npm run pinyin:record`）：

| 音节 | 为什么换不了字 |
|---|---|
| `ōng` | 汉语里不能独立成音节，也没有呼读字。拼音墙上仍借例词「松」发音 |
| `ēn`（恩） | ⭐ `ēn` 一声的常用字**只有「恩」**（「摁」是四声，其余生僻），无可替换 |

> `é`（鹅）即使读不准也**不影响教学**：它只用于单韵母 e，
> 而那一组按设计不教声调（见 `pinyinSyllables.ts` 的 `SINGLE_FINALS`），
> 选项上显示的是 `e` 不是 `é`。

> **为什么用 msedge-tts 包而不是自己实现协议**：
> 本来照 `generate-icons.mjs` 的路子手写了一版（Node 24 自带全局 WebSocket）。
> 实测**一律 403**：微软给这个端点加了 `Sec-MS-GEC` 时间戳签名，
> 而且比公开资料描述的更严——补上签名仍被拒（已排除时钟偏差）。
> 这是个**私有且在持续加固**的协议，手写实现等于埋雷。

### 3.3 拼音音节（阶段 ⑧ 已完成）

79 个音节，其中 **72 个有汉字载体、已入库**，7 个等真人录音。
见 `data/seed/pinyinSyllables.ts`。

#### ⭐ 关键决定：每个音节挂一个**汉字载体**

Edge TTS 是**文本**转语音，不是拼音转语音。喂它 `bā` 只能靠它猜怎么读；
喂**汉字**「八」则必然读对——常用字的读音是 TTS 的看家本领。

实测确认（`scripts/` 下的探针）：
- 裸拼音文本：四声能产出不同音频，但**不保证读对**
- 汉字：四声不同且必然正确
- SSML `<phoneme>` 音标覆盖：**不可用**（msedge-tts 会转义标签）

#### 选字的三条硬规矩

1. **绝不用多音字** —— 「乐」有 lè/yuè，「晕」有 yūn/yùn，TTS 挑哪个全凭运气。
   这是本表最大的风险来源，写表时已因此撤掉数个"看起来很合适"的字。
2. **优先常用字** —— 生僻字 TTS 也可能读错，且无法靠常识复核。
3. **`char` 与 `pinyin` 必须真的对应** —— 这一列就是给人复核用的：
   懂拼音的人扫一眼「bā → 八」就知道对不对，**不必听音频**。

#### 机器能验什么、不能验什么

| | 谁来验 |
|---|---|
| 声调标记与 `tone` 字段是否一致 | ✅ `pinyinSyllables.test.ts`（实际抓到过 `māng` 配 `tone: 2`）|
| 音节 key 有无重复、汉字是否单字 | ✅ 同上 |
| 同一个字有没有被标成两个读音 | ✅ 同上 |
| **「八」是不是真的读 bā** | ❌ **只能靠人耳** |

#### ⭐⭐ 实测教训：裸拼音会读错声调，已结构性修复

孩子试听后反馈：`á` 读成 `ā`、`ā` 读成 `à`、`ǎ` 读成 `á`、`ē` 读成 `è`、`ō` 读成 `ò`……
**全部出现在没有汉字载体的那批**——也就是只能把拼音串喂给 TTS 的那些。

这比没有声音严重得多：选项上标着 `ā`、播出来是 `à`，是在**明确地教错**，
而学错的发音以后很难改。三条修复：

| 问题 | 修法 |
|---|---|
| P1.3 四声调用裸元音 `ā á ǎ à` | ⭐ 改用「**妈麻马骂**」——教声调的标准范例，四个常用单音字，读音必然正确 |
| P1.1/P1.2 单韵母标了调 | ⭐ 改为**不带调**显示 `a o e i u ü`——课本introduce 单韵母时本就不标调，不作声调声明就无所谓读错 |
| d/n/l 呼读音 `dē nè lè` 无载体 | 一度改用真实音节「弟 你 里」，**已于 2026-08 撤回**，见下 |

另外补上了能找到的载体字：`凹`(āo)、`肮`(āng)、`椰`(yē)。

#### ⭐⭐ 2026-08 修正：呼读音不许拿例词顶替

上机反馈：拼音乐园里**声母 d 念的是「弟」**、n 念「你」、l 念「里」、
ei 念「飞」、ün 念「云」、eng 念「风」、ci 念「词」。

这是当初「宁可用常用字也不用多音字/生僻字」那条规矩用过了头。
呼读音是**老师带读时的那个音**，孩子在学校听 dē、在这里听 dì，
两套音互相干扰——而这面墙存在的全部意义就是给课堂做复习。
**「和老师一致」压倒「用常用字」。**

| 卡 | 之前（例词） | 现在（呼读音） |
|---|---|---|
| 声母 `d` `n` `l` | 弟 你 里 | **的 讷 乐** |
| 声母/整体认读 `c` `ci` | 词（cí，二声，z-c-s 三连里唯一的例外） | **呲**（cī，与 zī sī 齐） |
| 复韵母 `ei` | 飞 | **诶** |
| 前鼻韵母 `ün` | 云 | **韵** |
| 后鼻韵母 `eng` | 风 | **鞥** |

⭐ 这批字全部标 `soundOnly`（见 `domain/pinyin.ts`）：**只负责发音，
不进「听音选字」（P8.3）的选项**。「鞥」「讷」「呲」不在识字表里，
「的」「乐」是高频多音字——把它们摆成汉字选项，考的就成了辨认生僻字。
听音选**拼音**的题（P2/P4/P5/P8.1）不受影响：那些题的选项是拼音文字，
载体字只在背后发声，正是它该待的位置。

⚠️ **这批字必须人工复听**（`npm run pinyin:check`）：多音字（的/乐/诶）与
生僻字（鞥/讷/呲）正是 TTS 最容易读错的两类。读不准就往 `TAIL_FIX_KEYS` 里加，
仍不准则只能真人录（`npm run pinyin:record`）。

`ōng` 仍然没有呼读字，继续借例词「松」——它是拼音墙上唯一还标 `carrier` 的韵母卡，
由 `pinyinChart.test.ts`「声母韵母念呼读音，只有 ong 借例词」钉死。

> ⚠️ **改载体字必须重生成音频。** 脚本原本只补「文件不存在」的 key，
> 于是把载体从「ā」换成「啊」之后文件还在、直接跳过——表里改了，播出来还是旧的错音频。
> 现已改为按「念的文本变没变」判断（台账 `public/audio/voice/.spoken-text.json`），
> 改字必然触发重生成。

#### 试过但不可行的两条路

- **SSML `<phoneme>` 音标覆盖**：Edge 免费端点直接拒绝请求（`<phoneme>` 是 Azure 付费层功能）
- **自动测声调**：写过一个用基频曲线判定声调的分析器，结果 `鸡` 测出 12 个半音的下降、
  `大` 测出接近平调——**假阳性约五成**，因为单字音频有 1.5 秒静音尾巴，
  音高跟踪在衰减段产生倍频错误。做可靠需要正经的 DSP 工作，已放弃。
  **声调正确性目前只能靠人耳**，这就是 `pinyin:check` 存在的理由。

#### `npm run pinyin:check`

生成一张试听页（`public/pinyin-check.html`），把「听完全部音节」变成几分钟的事：
键盘 ← → 切换、空格重听、`1`/`2` 标记，最后一键导出问题清单。

> 校验时重点听：**声调是否分明**（尤其「妈麻马骂」这组）、
> **前后鼻音** `an/ang`、`in/ing` 是否读得出区别、**平翘舌** `z/zh` `c/ch` `s/sh`。
> 发现问题标记出来导出清单——换个载体字重跑 `npm run voices` 即可，
> 台账会自动识别载体变更并重生成。

### 3.4 英语（阶段 ⑨ 已完成）

**158 条**词/短语/整句/字母，全部用英语儿童音色生成，见 `data/seed/englishWords.ts`。

#### 与拼音的关键差别：不需要发音载体

拼音那边每个音节要挂一个汉字，因为把 `bā` 喂给中文 TTS 只能靠它猜。
英语反过来——**喂英文单词给英语音色是母语场景，必然读对**，
`apple` 不存在读成别的可能。所以英语的内容成本远低于拼音：
不用挑载体字、不用怕多音字、不用逐条试听。

#### ⭐ 字母念整句「A is for apple.」

孤立的单个字母**有歧义**：`A` 既是字母名 /eɪ/ 也是冠词 /ə/，TTS 挑哪个不由我们决定。
这是英语侧唯一有发音风险的地方，解法是**把字母放进整句**——
`A is for apple` 里那个 A 只可能是字母名，歧义直接消失，
不必像拼音那样逐条人工试听。

而且这句话本身就是字母教学的标准句式：字母与首字母单词一次带出。

> ⚠️ 字母是脚本里唯一需要**重建**的一段：`LETTER_CARDS` 由规则拼出，
> 正则扫不到成品。脚本 `loadLetters()` 从 `WORDS` 表解析并按同样的句式拼接，
> 结构对不上时**直接失败退出**（不是警告）——
> 静默不同步的后果是「代码改了、播出来还是旧的」，拼音那边已经踩过一次。

#### 一处已知的冗余

`orange` 生成了两条音频（`en.orangeColor` / `en.orangeFruit`），
因为颜色和水果的图形面不同（🟧 / 🍊），而一个词条只能有一个图形面。
多出来的一条约 10KB，不值得为它引入「多词条共用一个片段」的间接层。

### 3.5 识字与古诗（2026-08 新增）

语文区三块浏览页的语音，共 **663 条**：识字 300 条（3 辑 × 100）
+ 古诗 362 条（60 诗题 + 242 句 + 60 译文）+ 拼音墙补的 `pinyin.fei1`。
内容见 `data/seed/hanziCards.ts` 与 `data/seed/poems.ts`。

> 诗句 242 条而不是 240：《游子吟》是六句，`lines` 本来就不限长度。
> 按「首数 × 4」估条数会差这么两条，以脚本实际输出为准。

> 两次扩容都在 2026-08：识字从 100 扩到 300（她把第一辑全认下来了），
> 古诗从 20 扩到 60（+242 条）。加内容连带要改三处硬编码的数量断言——
> 测试（`hanziCards.test.ts` / `poems.test.ts`）、
> `generate-voices.mjs` 的 `EXPECTED_HANZI_COUNT` / `EXPECTED_POEM_COUNT`，
> 以及本节这个数。漏掉第二处的后果是脚本直接硬失败（这是故意的，见 §5.2）。

**语速单独放慢到 `-25%`**（`RATE_RECITE`）。这两类内容孩子是**跟着念**的，
不是听个大概——常速下她跟不上，只能听完再回想，那就从「跟读」退化成「听广播」。
⚠️ 没有用字母卡那档 `-30%`：字母慢是因为每个音都陌生，
而这里念的是她天天听的中文，过慢反而拖沓、像在哄小小孩。

#### ⭐ 识字不念孤立单字，念「天。蓝天的天。」

这是**拼音那边用学费换来的同一条结论**（见 §3.3）：孤立单字没有语境，
TTS 既可能挑错多音字的读音，声调也读得发飘。
拼音的解法是换汉字载体，识字的解法是**把字放进一句话**：

```
朗读文本 = `${char}。${word}的${char}。`      domain/hanzi.ts 的 hanziSpokenText()
```

一次解决两个问题：

1. **消歧** —— 「地」在「大地的地」里只可能读 dì，不会读成助词 de；
   「长」在「长短的长」里只可能是 cháng。**少 shǎo · 好 hǎo** 同理
2. **教学上本来就该这么念** —— 「XX 的 X」是课堂上认字的标准说法

> ⚠️ 所以 `word`（组词）不是装饰，是**朗读句式的一部分**。
> 组词里没有那个字，念出来就是「天。苹果的天。」这种句子。
> `hanziCards.test.ts` 逐字校验组词必须包含该字。

#### ⭐ 片段 key 用汉字码点，不用拼音

`hanzi.u5929`（天）而不是 `hanzi.tian1`。这 300 个字里同音同调的远不止一对
（**十/石** shí、**木/目** mù、**师/狮/诗** shī、**舌/蛇** shé、
**元/园/圆** yuán、**生/声** shēng、**快/筷** kuài），
拼音撞车会让两个字共用一条音频，
表现是「点『石』念出『十』」——静默，且只有懂拼音的人才发现得了。

> 字表越大这个隐患越密：第一辑只有 2 对同音同调，扩到 300 字后有 7 组。
> 当初选码点而不是拼音，省掉的正是这次扩容里最难查的一类 bug。

#### ⭐⭐ 古诗：多音字一律改写（2026-08 修订，方针是拿错音换来的）

古诗里的多音字，TTS 只能按上下文猜。对策与拼音那边同源——**改喂同音字**，
屏幕上显示的永远是原文，只有送去合成的那份被换了字：

```
PoemLine.spoken    改诗句      「曲项向天歌」→「屈项向天歌」
Poem.headSpoken    改报诗名句   「咏华山。宋，寇准。」→「咏化山。宋，寇准。」
```

⚠️ **这里原本的方针是「只改几乎必然读错的，其余留待人工听」。上机试听把它推翻了**：
《回乡偶书》「鬓毛衰」念出来是 **cuī** —— 那是这首诗的古押韵音，而教材注 shuāi。
也就是说这套 TTS 念古诗时会主动往**古音**上靠，
「此处读的正是现代最高频音」根本不能当安全条件。

于是改成：**只要是多音字，能换字的一个不留**。孩子第一次听到的音会跟着她很久。

换字的三条要求，按优先级：

| | 要求 | 说明 |
|---|---|---|
| 1 | 同音同调 | 这是全部意义所在 |
| 2 | 换上去的必须是**单音字** | 拿一个多音字换另一个多音字，等于没换 |
| 3 | 尽量让句子仍读得通 | 「万崇山」比「万虫山」好，但**读得通让位于读得准** |

目前 34 处（诗句 29 · 诗题 5），全表在 `poems.ts` 各句旁边的注释里。典型几例：

| 原文 | 喂给 TTS | 为什么 |
|---|---|---|
| 乡音无改鬓毛**衰** | 鬓毛**摔** | shuāi，实测念成了 cuī ⭐ |
| 远上寒山石径**斜** | 石径**协** | xié，古诗里 TTS 会走 xiá 的旧读 |
| 天似穹庐，**笼**盖四野 | **拢**盖四野 | lǒng（笼罩），会读成笼子的 lóng |
| 怕**得**鱼惊不**应**人 | 怕**德**鱼惊不**映**人 | 一句两个坑：dé（会读轻声 de）· yìng（会读 yīng） |
| 咏**华**山。宋，寇准。 | 咏**化**山 | huà，诗题只能靠 `headSpoken` 改 |
| 江南。汉，汉**乐**府。 | 汉**月**府 | yuè，作者名同样够不着 `spoken` |

**三处没有同音字可换**，汉语里 `sàn` 只有「散」、`mǒ` 只有「抹」、`lè`（勒）的同音字
只剩生僻的「泐」（换上去 TTS 更可能按声旁乱读）：
《村居》儿童**散**学 · 《饮湖上初晴后雨》淡妆浓**抹** · 《敕勒歌》诗题的**勒**。
这三处保留原文，只能靠耳朵。

> ✅ **2026-08-24 全部人耳复核通过**：34 处改写生效，三处无字可换的
> TTS 自己也读对了。所以「换不出同音字」不等于「一定读错」——
> 下次遇到同类情况，先听再决定要不要为它冒改写的风险。

`poems.test.ts` 守四条：改写不改变字数 · 改写与原文**只差个别字**（≤3 字，
否则就不是换字而是重写）· 已有改写**只增不减**（删一处就是放一个错音回来）·
`headSpoken` 与报题句字数一致。

#### 🎧 `npm run poem:check` —— 读音校验页

机器验不了声调，只有耳朵能验，所以照拼音校验页做了一个同样的东西：

```
把 60 首里所有含多音字的句子挑出来（当前 138 条），按风险排序
未改写的排最前并标红 · 已改写的排后面（要验证换的字真把音掰回来了）
标红目标字 + 标注该读什么 + 显示实际喂给 TTS 的文本
键盘 ← → 逐条听，1 标「读错了」，最后一键导出清单
```

> 生成到 `public/poem-check.html`，`npm run dev` 后访问 `/poem-check.html`。
> ⚠️ 它读的是 `public/audio/voice/*.mp3`，所以要先 `npm run voices`。

#### 一句诗一个片段，不是整首一条

「读整首」是把 `wholePoemUtterance()` 排给播放器（正好是 §2.2 那套拼接机制），
「只读这一句」直接取其中一条——**同一份素材两种用法**，不必为整首再合成一遍。

#### ⭐ 读整首从「静夜思。唐，李白。」报起

诗题那一条片段念的是**整句报题**（`poemHeadText()`），不只是诗名——
报出诗名、朝代、作者本来就是背诗的一部分，课堂上带读、孩子上台背诵，
开口第一句都是它。只念诗文等于把这首诗从它的来处剥离出来了。

⚠️ 这句话的拼法在两处各有一份（`domain/poem.ts` 的 `poemHeadText()` 与
生成脚本的 `loadPoems()`），必须**逐字相同**——差一个标点，
60 首诗每次跑 `npm run voices` 都会被判定「文本变了」而重新合成一遍。

#### ⭐ 句间停顿 0.4 秒，不是默认的 80ms

上机反馈「相邻两句间隔太快了」。根因是播放器的默认间隔 `GAP = 0.08`
按的是**一句话内部的词**（「9」「加」「5」不黏在一起就行），
而整句与整句之间完全是另一个量级——四句连着念像一口气赶完。

取值有实测依据：逐帧扫诗题片段「静夜思。唐，李白。」内部的静音，三首取样一致——

| 位置 | 停顿 |
|---|---|
| 「静夜思」**。**「唐」 | 0.85 / 0.89 / 0.89 秒 |
| 「唐」**，**「李白」 | 0.36 / 0.34 / 0.40 秒 |

取**逗号那一档**（`POEM_LINE_GAP = 0.4`）：句号档是「一段话说完了」的停顿，
用在句间会把一首五言绝句拖成四段独白；逗号档正是同一首诗里上下句之间的自然换气。

机制是 `Utterance.gap`——**只有需要的语句才覆盖默认值**，
题干、鼓励语那些一句话内部的拼接仍然走 80ms。
由 `poem.test.ts` 钉住上下限：低于 0.24 等于没加，高于 0.85 就不像同一首诗了。

诗单只预取**当前那一辑**的 20 条诗题，全文在点进那一首时才取（`PoemView`）——
60 首的全部句子一次拉完是两百多条，在 iPad 上会卡一下。

#### 生成脚本

`loadHanzi()` / `loadPoems()` 按行扫 seed 文件。
⚠️ **古诗是逐行状态机而不是一条大正则**：句子的 key 里带序号（`poem.jingyesiL2`），
而序号是「这一句在这首诗里排第几」，正则拿不到这个上下文。
所以 `poems.ts` 要求**每句 `l(...)` 独占一行**，折行会让编号错位——
后果是「点第三句、念出第二句」。

⚠️ 分辑之后，辑的声明里也有 `id: 'vol1',`，与诗的 `id:` 长得一样。
脚本靠 **`vol` 前缀**把它认出来跳过，否则下一首诗的片段会全落到 `poem.vol1L*` 上。
诗的 id 因此不许以 `vol` 开头，由 `poems.test.ts` 拦。

两个解析器都在条数对不上时**直接 exit 1**（识字必须 300、诗题与译文必须各 60），
与字母、宠物台词几处的硬失败保护一致。
